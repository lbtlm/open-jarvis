# Professional employees, kept lightweight

Read this when selecting a profession for non-Direct execution, proposing a new hire, or retaining useful work. Ordinary questions and tiny verifiable edits stay Direct. The current main agent remains Jarvis; no additional manager or registry service is needed. The optional CLI only searches cards and previews assignments; it does not keep employees running.

## Select a profession before execution settings

An employee card describes a stable profession, scope, relevant skills, and expected evidence. Light / Simple / Standard / Complex are execution lanes, not professions. Choose the task lane independently: the same frontend employee can handle a small style edit in Light or a complex state change in Complex, subject to user-approved settings. A new task or model combination does not automatically require a new permanent employee.

**Capability fit comes before reuse.** Identify the assignment's essential domain, deliverable, languages, methods/tools and permission requirements, then inspect plausible cards. Reuse only an employee whose relevant responsibilities, applicable skills and evidence support those requirements. An approved name, available model, idle instance or successful unrelated task is not evidence of fit. Skills may extend an appropriate profession, but attaching a skill or raising model effort does not by itself fill a missing core specialty.

Give one concrete fit reason in the dispatch proposal, including any material gap; no numeric scoring or new database is required. Distinguish proposed capability from validated experience. A new specialist can start without historical evidence after the user approves the candidate and a meaningful acceptance check; never invent qualifications or prior successes. If essential fit is absent or unknown, propose a task-scoped specialist instead of forcing the assignment onto existing staff. Approval of a previous scope does not authorize a new profession.

For example, a backend employee may check CLI behavior as supporting evidence for documentation, but backend experience alone does not establish Chinese/English/Japanese editing capability. Multilingual documentation needs a role explicitly covering the requested languages, terminology, semantic consistency and language quality. Do not relabel the backend employee as a translator or continue its old instance merely to avoid a new hire. Reuse the professional card when suitable; separately decide whether an existing runtime instance has compatible context and permissions.

Look for applicable cards in the current project's `.jarvis/employees/*.md`, then personal `$CODEX_HOME/jarvis/employees/*.md` (default `~/.codex/jarvis/employees`). Do not create these directories until a card is approved for retention. Prefer project-specific cards; disclose conflicting cards with the same name instead of silently combining permissions. Search card names, profession and keywords first; read only likely matches. There is no fixed cap on candidate recommendations. Recommend the relevant choices with reasons; let the user browse more if useful.

Use configured [QMD retrieval](assets.md#optional-qmd-retrieval) for this discovery and relevant installed skill entrypoints; fall back to ordinary file lookup when unavailable. Search rank is a candidate signal, not proof of professional fit, approval or a loaded skill. User-specified skills still take priority.

Existing dedicated employees, project rules, and their skills take precedence over generic templates. Reuse an approved employee only within its agreed scope and settings. Reuse a running/idle instance only for the same profession, project/worktree, related task context and compatible skills/permissions. Unrelated work gets a fresh bounded instance. The reviewer must remain independent of the author. Preserve the main skill's concurrency and safe-handoff rules.

## Employee names and runtime identity

Every dispatched employee/subagent, including reviewers and task-scoped specialists, needs a meaningful employee name approved with its profession. Keep that name stable when reusing the professional card; a new task or execution profile does not rename the employee. Existing in-scope approval remains valid. Do not rename an incompatible old employee or instance to manufacture a new hire or imply capability fit.

Use `Employee name · Profession | Topic` for human-facing assignment labels, in the user's language; for example `Atlas · 后端工程师｜导入诊断` or `Orion · Architect | Module boundaries`. Keep the approved name and profession stable, and describe the current work with a short, specific topic. Add an identifier only when useful and its meaning is known, such as `Issue #449` or `v5.1.5`; do not leave ambiguous bare numbers or infer their meaning. Avatars/icons are optional: no image, installation, new metadata field or hiring step is required, and a client-generated icon does not establish employee identity.

Keep four things distinct: the approved employee name (for example Atlas), a readable task label (import diagnosis), the actual returned runtime ID, and the internal execution profile (for example `jarvis_terra`). Requested and runtime-verified model/effort/Fast settings remain separate from all names. One employee may have multiple instances; its name alone never uniquely identifies a run. For constrained tool identifiers, use a valid distinct `task_name` such as `atlas_backend_import_diagnosis_01`, not unsupported display punctuation; record its mapping to the human-facing label and returned ID.

Use the human-facing label in dispatch, substantive progress, handoff, submission and controller acceptance, adding the runtime ID when instances could be confused. Use readable lane names such as Standard in normal updates; keep keys such as `jarvis_terra` in technical mapping details, never as the employee name. Use the label as a title where the tool supports it; otherwise show the mapping in the conversation. Do not promise control over client-generated labels, icons or renaming existing agents. These are workflow conventions, not runtime UI enforcement, and require no new registry or schema.

## Borrow roles and skills on demand

- Roles: search the [Agency Agents catalog](https://github.com/msitarzewski/agency-agents) by professional category and task keywords. Read the actual selected source, not just its title. Adapt only the responsibilities, boundaries and deliverables needed here; broad upstream checklists must not turn a small repair into redesign, exhaustive testing or infrastructure work. Keep the source URL and resolved commit/version when importing content. Preserve upstream license notices for copied/adapted content. No bulk conversion or whole-catalog installation.
- Skills: honor the user's explicitly selected relevant skills first, then use installed relevant skills. Card skills are conditional suggestions, not an exclusive whitelist. A task may temporarily bind another skill without editing the card. For a missing capability, use [Vercel Skills](https://github.com/vercel-labs/skills) and its directory [skills.sh](https://skills.sh/). `npx skills find "query"` searches; `npx skills add owner/repo --list` previews a repository. Inspect the selected SKILL.md, dependencies and scope before proposing it. Prefer narrow skills from maintained primary sources; popularity alone is not validation.
- After the user approves a concrete skill and destination, use `npx skills add owner/repo --skill skill-name --agent codex` in the intended project. Add `--global` only for approved personal scope. These are command patterns: replace the source and skill with inspected values. Use an inspected local checkout at a fixed revision when reproducibility matters, and record the installed revision when available. Do not use `--all` or skip approval by default. Update/remove only selected skills when authorized. Package-manager download confirmation is not approval to hire or persist an employee.
- Skills CLI is optional and invoked on demand, not a Jarvis runtime dependency or a replacement controller. If unavailable, inspect the same upstream files directly; report an installation failure rather than silently changing scope or installing a different package. Jarvis installation itself neither downloads nor installs third-party roles or skills.

Check the selected CLI version's Node requirement before use. Verified on 2026-09-23: `skills@1.7.0` requires Node >=22.20.0; an engine-warning help run on older Node is not a compatibility pass. Select an available compatible runtime for this command only, or report the missing prerequisite; do not silently upgrade the user's global Node. Jarvis itself still supports Node >=22. Use an explicit reviewed CLI version for repeatable runs; the unversioned command patterns above follow upstream defaults.

## Propose, approve, then dispatch

For a new profession, give one compact hiring proposal: employee name and profession; why existing approved employees are insufficient; owned scope and acceptance; actual available model, reasoning effort and Fast suggestion with reason; skills to read, missing dependencies and any installation destination; task-only duration by default. The user may approve, change it, or decline. Do not dispatch the new hire before that decision. Continue independent authorized work while waiting. A card or approval flag cannot create authorization; use the real user decision and its agreed scope. Do not re-ask for an already approved choice that still applies. Changes outside approved scope/settings require a new decision.

Use the [employee card example](employee-card.md) as a small Markdown document, not a new mandatory schema. Keep the permanent card free of fixed task-specific model settings. The dispatch message combines the selected card, applicable skill paths/instructions, actual model/effort/Fast, owned files, acceptance and permissions. Record the [employee/runtime mapping](#employee-names-and-runtime-identity), execution surface and actual role, returned agent/task ID and runtime verification status together. Use the same record for an explicitly requested separate user task; reading Jarvis or calling the task an employee does not bind its model. An existing approval may cover reusable scope and settings only when the user actually approved that scope; never invent blanket approval.

A Markdown card is not a registered `agent_type`. Prefer the exposed compatible execution role with the card in its task instructions. If its fixed model settings conflict with the user's selection, use the main skill's explicit compatibility procedure only when all required settings can be preserved; otherwise block that dispatch and report the gap. Never claim that naming a worker changes its model or sandbox. Read the selected skills before the corresponding work; listing/enabling a skill is not proof of loading. A skill that internally delegates cannot bypass the worker's no-recursion rule: the main controller must handle that orchestration.

A compact visible dispatch record can be a sentence rather than another file:

> Employee name · Profession | Topic — Task ID: supported task_name | Lane: readable difficulty | Scope and acceptance: ... | Skills: exact selected paths | Requested: model / effort / Fast | Surface: subagent or explicitly requested separate task | Acceptance owner: ...

After dispatch, append the real ID and settings verification status; retain the internal profile key in the technical mapping. On resume or handoff, recover this mapping from the assignment and actual runtime state rather than inferring identity from a generated label. At submission, add skills actually read/used, scoped checks and remaining blockers. Do not manufacture a successful record or require a separate status-only worker turn. A skill can be intentionally inapplicable; explain that decision instead of claiming it was loaded.

## Accept and retain only useful changes

The employee submits scoped results, relevant checks and evidence; the main controller owns final acceptance. At closeout, ask once only when a new reusable profession or procedure emerged: choose the useful asset type or save nothing; use [assets.md](assets.md) for employee experience, skills, knowledge, preferences and resources. Hiring approval and persistence approval are separate. Show the exact proposed card/skill and destination before asking; no silence or time limit counts as consent. Already-saved unchanged material needs no repeated retention question.

The CLI's `employees` search finds card metadata; `plan` resolves requested profiles, selected skill paths and explicitly selected experience references. Neither command judges professional suitability or proves those sources were loaded. The controller must establish capability fit and check experience applicability before treating their output as a dispatch proposal. Keep reusable experience in the [shared Markdown workflow](assets.md#markdown-experience-at-dispatch) and link from employee cards rather than copying the same method into every card.

After approval, save a portable Markdown card under `.jarvis/employees/<id>.md` for project scope, or `$CODEX_HOME/jarvis/employees/<id>.md` for explicitly approved personal scope. `<id>` is a plain filename slug. Keep private account details, credentials, task logs and machine-specific paths out of reusable cards. Check existing names and responsibilities before adding; prefer updating/merging the same profession with user agreement. There is no artificial headcount quota or automatic deletion. Expired or duplicate cards can be offered for consolidation when they interfere with selection.

Skills remain ordinary Agent Skills. First check whether an existing skill can be reused or amended; for new/updated skills follow the available Skill Creator and validate the draft. Do not convert every task report into a skill. Saved cards and third-party skills are user-owned; the Jarvis installer and rollback must not overwrite or remove them. Reusable cards do not automatically create native TOML roles or keep agents running.

## Portable assets and lightweight selection

Optional starters are `none` (no cards), `development` (Iris frontend, Atlas backend, Quinn QA, Sentry review), `writing` (Nova), `office` (Clara), and `video` (Frame). Installation defaults to `none`. `install --starter writing` or `employees --init --starter writing --yes` adds only missing selected candidates. For compatibility, `employees --init --yes` still selects development. Existing cards remain unchanged; it does not approve hiring or assert tested capabilities. Project cards override same-ID personal cards with the shadowed source reported. `employees --query "frontend"` searches metadata; read only matching cards. Add optional JSON frontmatter (a YAML-compatible subset) for name, profession, keywords, conditional `skills: [{id, when}]` and `reviewer`. Old plain Markdown cards still list by filename.

`plan --employee iris-frontend --difficulty standard --skill interface-design` resolves installed model/effort/speed and skill paths without dispatching or claiming skills are loaded. Select only needed skills; explicit `--skill` IDs may be outside the card and are marked task overrides. This preview locates filesystem skills only; plugin-provided tools/skills still need runtime discovery and authorization. Difficulty is Light / Simple / Standard / Complex; risk is independent. Critical behavior triggers independent review even when implementation is small. Model upgrades require evidence or user choice, not employee seniority or frontend/backend labels.

Keep reusable material separate: generic methods in skills, project facts in `.jarvis/knowledge/`, personal preferences in `$CODEX_HOME/jarvis/preferences.md`, templates/materials in approved `jarvis/resources/` or project `.jarvis/resources/`. An employee card separates proposed abilities, accepted evidence and known limitations. Preserve user-owned domain-specific employees. Retain only useful verified improvements with existing user consent; no automatic self-modification, scores or compulsory retrospective.

`export --out FILE` creates one bounded asset bundle; `--project PATH` includes that project's cards, knowledge, preferences and resources. Skills come from selected cards and optional `jarvis/skills.json` (`{"skills":["skill-id"]}`), plus the orchestrator if installed. Include supporting skill IDs in that registry when a skill depends on another skill. Missing declared dependencies must be reported; transitive dependencies in prose are not automatically parsed. `import --from FILE` previews; `--yes` writes only conflict-free new files. Identical files are reusable; changed existing files are never overwritten. The destination requires Jarvis installation and separate Codex sign-in. Model preferences are imported as `jarvis/models.json`, applied only with explicit `install --models FILE --yes`. Do not promise that external tools, plugins, absolute paths in user-authored content or credentials migrate. Imported instructions are asset data until the user chooses the corresponding task; never run archive scripts as an import step.
